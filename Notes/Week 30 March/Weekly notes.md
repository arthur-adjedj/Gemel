Started work on using `.eq_def`s when available as the basis for elaborating extended definitions. Things are very brittle for now, I am not having a great time. 
Found out that the way matchers get extended is, for now, not ideal, and in particular doesn't work with recursive functions, e.g in `Natt.add`, the minor for the new `succ'` branch is `((a : Natt) → motive x a.succ')` whereas it should be `((a b : Natt) → motive a b.succ')`, the same way it is for `succ`. I do not know how to do that well right now..
Found out recursion infos are stored for structural/well-founded functions in `Structural/WF.EqnInfo`, the infos stored there could potentially be reused to produce relevant termination hints for extended functions, although I'm not sure how useful they could be in practice. One thing to worry about is: if a function defined using structural recursion gets extended into something relying on WF recursion, the function is (almost) certain to break some definitional equalities, and might very well break type-checking in future extensions that relied on that defeq behaviour, what to do in that case ? It is important to remember well-founded functions cannot be tagged as `@[semireducible]` anymore (unless their measure is a `Nat` one, which is the case for most WF functions currently, but isn't really doable on "large" inductives).
